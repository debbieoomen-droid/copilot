Quick Decision Tree

Start here when deciding which customization type to use

1

Should this apply to EVERY interaction?

Think: coding standards, project conventions, response style preferences

YES →

Use: .github/copilot-instructions.md

Always loaded, applies universally across the entire repository

2

Should it apply only to SPECIFIC file types or directories?

Think: Kotlin rules for .kt files, Java rules for .java files, Gradle conventions for build.gradle.kts

YES →

Use: .github/instructions/*.instructions.md

Conditionally loaded based on applyTo glob patterns

3

Is it a REUSABLE task you'll invoke manually?

Think: scaffolding REST endpoints, generating service tests, code reviews

YES →

Use: .github/prompts/*.prompt.md

Loaded only when you type /prompt-name

4

Is it a COMPLEX workflow with scripts/resources?

Think: debugging CI/CD, security reviews, multi-step processes

YES →

Use: .github/skills/*/SKILL.md

Auto-loaded when description matches, includes bundled resources

5

Is it a PERSISTENT persona for specific workflows?

Think: "Backend Expert", "Security Reviewer", "Incident Debugger"

YES →

Use: Custom Agent

Explicitly selected, orchestrates multiple skills and tools

.github/copilot-instructions.md — Banking Backend Platform Example 
# .github/copilot-instructions.md

# Project Overview
Backend services platform for payments, customer onboarding, and transaction processing.
Microservices architecture: API Gateway → Spring Boot services → Kafka → PostgreSQL.
Handles payment orchestration, account validation, ledger integration, and audit trails.

# Tech Stack
- Languages: Java 21, Kotlin 2.x
- Framework: Spring Boot 3, Spring MVC, Spring Data JPA
- Build: Gradle with Kotlin DSL
- Messaging: Kafka
- Database: PostgreSQL 15
- Testing: JUnit 5, MockK/Mockito, Testcontainers

# Universal Coding Standards
- Prefer constructor injection; never use field injection
- Keep controllers thin and move business logic into services/use cases
- Use immutable DTOs and explicit validation annotations
- Prefer Kotlin data classes and null-safety in .kt files
- Never log sensitive financial data (IBAN, account IDs, balances, tokens)

# Build Commands
- Development: `./gradlew bootRun`
- Build:       `./gradlew build`
- Test:        `./gradlew test`
- Verify:      `./gradlew check`

# Response Preferences
- Keep responses concise (under 10 lines when possible)
- Show Kotlin examples for .kt files and Java examples for .java files
- Prefer Gradle Kotlin DSL snippets over Maven XML

# .github/instructions/kotlin-service.instructions.md
---
        applyTo: "src/main/kotlin/**/*.kt"
---

        # Kotlin Service Guidelines
        - Prefer data classes and sealed interfaces for DTOs and result types
        - Keep nullability explicit; avoid !! unless there is a hard invariant
        - Use constructor injection and keep Spring annotations minimal
        - Keep controllers orchestration-only; business rules stay in services
        - Never expose or log raw financial identifiers or tokens


        # .github/instructions/java-service.instructions.md
---
        applyTo: "src/main/java/**/*.java"
---

        # Java Service Guidelines
        - Use Spring Boot for controllers, services, and scheduled jobs
        - Prefer records for simple request/response DTOs when appropriate
        - Use Bean Validation annotations for request validation
        - Isolate mapping logic; do not mix persistence entities with API contracts
        - Document public endpoints with OpenAPI annotations when the service exposes REST APIs


        # .github/instructions/gradle.instructions.md
        ---
        applyTo: "build.gradle.kts,settings.gradle.kts,gradle.properties,gradle/libs.versions.toml"
        ---

        # Gradle Build Guidelines
        - Prefer Kotlin DSL for new build logic
        - Keep dependency versions centralized in version catalogs where available
        - Use custom Gradle tasks for repeatable developer workflows
        - Avoid plugin sprawl; justify each plugin with a concrete need
        - Keep CI commands aligned with ./gradlew clean build test check


# .github/instructions/testing.instructions.md
---
        applyTo: "src/test/java/**/*.java,src/test/kotlin/**/*.kt,**/*Test.java,**/*Test.kt"
---

# Testing Standards
        - Use JUnit 5 for test orchestration
        - Prefer MockK for Kotlin and Mockito for Java where mocking is needed
        - Use Testcontainers for database and Kafka integration tests
        - Test observable business behavior, not framework internals
        - Each test should be deterministic and independent

api-security-review.prompt.md 
---
agent: 'agent'
description: 'Security review for API endpoints'
---

# API Security Review
Review the selected API code for vulnerabilities:

1. Authentication/Authorization
  - OAuth 2.0 / OIDC token validation
  - Role-based access control (customer vs. employee vs. batch)
  - Service-to-service trust boundaries and token propagation

2. Input Validation
  - Bean Validation coverage and missing constraints
  - Unsafe deserialization or mass assignment risks
  - IBAN, account number, and payment reference validation

3. Data Exposure
  - PII and financial data (IBAN, balance) in responses and logs
   - Error message information leakage
  - Accidental logging of transaction amounts, account IDs, or tokens

4. Rate Limiting
   - Payment endpoint protection
  - Brute-force, replay, and enumeration mitigation

5. Backend-Specific Risks
  - Missing idempotency handling for payments
  - Transaction boundary issues and inconsistent retries
  - SSRF or unsafe outbound calls to downstream services

Provide line numbers and remediation steps.

In Copilot Chat, type /new-api-endpoint and you'll be prompted for the language and feature name. The prompt file guides Copilot to generate controller, service, DTO, and test files according to your backend standards.

.github/skills/gradle-build-debugging/SKILL.md 
---
    name: gradle-build-debugging
    description: Debug failing Gradle builds for Java and Kotlin services. Use when
      CI/CD fails, builds break, dependency resolution loops, or tests do not start.
    ---

# Debugging Process

1. Identify the failure
      - Check the failing Gradle task
      - Identify whether the issue is compile, test, dependency, or plugin related
      - Review stack traces and the first meaningful error

2. Analyze logs
      - Use scripts/collect-gradle-scan.sh to capture task output
      - Check references/common-gradle-errors.md
      - Inspect Java version, Gradle wrapper version, and dependency lock state

3. Common Issues & Fixes
   
      Issue: Dependency conflict
      - Check version catalog and transitive dependency trees
      - Run `./gradlew dependencies`

      Issue: Test failures in CI only
      - Check containerized test assumptions and port collisions
      - Use `./gradlew test --info`

4. Fix and validate
      - Apply fix locally first
      - Re-run the failing task in isolation
      - Run `./gradlew clean build` before pushing

# Available Resources
    - scripts/collect-gradle-scan.sh   - Capture build diagnostics
    - scripts/verify-wrapper.sh        - Validate wrapper and Java version
    - references/common-gradle-errors.md - Known issues

Backend Expert — Custom Agent Configuration 
## Behavior
You are a backend development expert for banking applications, specializing in:
- Java 21, Kotlin 2.x, and Spring Boot 3 services
- Gradle build logic and dependency management
- Secure API design, validation, and transactional consistency
- Kafka-based event processing and resilience patterns
- Performance tuning for synchronous and asynchronous service flows

## Approach
1. Keep controllers thin and business logic inside services or use cases
2. Prioritize correctness, observability, and safe failure behavior
3. Prevent leakage of IBANs, account IDs, balances, and tokens in logs and responses
4. Prefer idempotent designs for payment and transfer operations
5. Validate with unit tests and integration tests before proposing larger refactors

## When helping with code:
- Suggest Kotlin for .kt files and Java for .java files
- Recommend constructor injection, explicit validation, and transaction boundaries
- Flag missing retry, timeout, circuit breaker, and idempotency handling
- Add Gradle commands when verification matters
- Prefer Testcontainers for realistic integration tests

## Skills to use:
- gradle-build-debugging
- security-audit
- performance-analyzer

Unlike skills that activate automatically for specific tasks, agents are personas you select that maintain consistent behavior across an entire session. They can orchestrate multiple skills and have persistent priorities.

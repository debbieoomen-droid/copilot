Part 1 — What we do together today

Three exercises. Everything is copy-paste; you don't need to invent prompts.

IN SESSION 1 · Weak vs strong prompts 15 min

exercises/backend/01-weak-vs-strong-prompts.mdexercises/frontend/01-weak-vs-strong-prompts.md

Ask Copilot for a Dutch BSN validator with a lazy one-line prompt, look at what you get, then run the fully specified version and compare. Then actually run the result — Step 4 — and feed both versions a number that has nine digits but fails the elfproef. Only one of them notices.

Every other technique today is a variation on this one idea: the tool is as good as what you tell it.

IN SESSION 2 · Copilot on real backend work 35 min

exercises/backend/02-backend-copilot-modules.md — Step 0, then pick two of 1.1, 1.2, 1.5

Open project/backend/ as your VS Code folder, then start it: mvn spring-boot:run (or .\mvnw.cmd spring-boot:run if you don't have Maven installed)

  • Step 0 (8 min, everyone) — three #codebase questions to orientate yourself in a codebase you've never seen, then check which files Copilot actually read
  • 1.1 — add a service method that finds one agent's cases from the last 7 days
  • 1.2 — add a PATCH /assign endpoint so an agent can claim an open case (only when it's still OPEN)
  • 1.5 — generate JUnit tests for the existing updateStatus business rules

IN SESSION 2 · Copilot on real frontend work 35 min

exercises/frontend/02-prompting-in-the-app.md — Step 0, then pick two scenarios

Open project/frontend/ as your VS Code folder, then right-click index.html → Open with Live Server

  • Step 0 (8 min, everyone) — three #codebase questions to orientate yourself in a codebase you've never seen, then check which files Copilot actually read
  • Scenario A — implement the notification banner (it's an empty stub; the app already calls it everywhere)
  • Scenario B — close a real XSS hole in the case card (js/components/case-card.js)
  • Scenario C — find and fix 3 planted bugs in the priority-score function, then watch the case list reorder
  • Scenario D — document undocumented code for a new joiner

IN SESSION 3 · Build your own reviewer agent 25 min

exercises/backend/03-build-a-reviewer-agent.mdexercises/frontend/03-build-a-reviewer-agent.md

Write one file that turns Copilot into a reviewer that works the way your team reviews — then test it on deliberately bad code, once without the agent and once with it, and compare.

This is the one to take home. A review standard written down once beats a review standard everyone remembers differently.

Part 2 — Extra labs, already written

Your exercise file contains a full three-module curriculum. We only use Module 1 today — everything below is already written and waiting in exercises/backend/02-backend-copilot-modules.md.

EXTRA Module 1 — the two we skip ~25 min

  • 1.3 — refactor maskIban() under explicit performance constraints
  • 1.4 — generate a custom repository query with @Query (JPQL)

EXTRA Module 2 — Architecture, Understanding & Reviews ≈1 hour

  • 2.1 — have Copilot explain this application's architecture to a new joiner, then judge whether it's actually right
  • 2.2 — write an Architecture Decision Record (ADR) for the choice of an H2 in-memory database
  • 2.3 — architecture trade-off analysis
  • 2.4 — review a proposed bulk-delete endpoint for correctness, security and standards
  • 2.5 — generate onboarding documentation for the whole service
No code is written in most of these — you're using Copilot to explain and document, which is where a lot of real time goes.

EXTRA Module 3 — Responsible Use, Security & Risk ≈1 hour

  • 3.1 — spot the security vulnerabilities in a case-search endpoint (SQL injection)
  • 3.2 — hardcoded credentials and secrets: find them, then fix them properly
  • 3.3 — validate Copilot's test output (do the tests actually prove anything?)
  • 3.4 — prevent data exposure in API responses
  • 3.5 — responsible prompting for sensitive business logic
  • 3.6 — AI limitations awareness: find the edges deliberately

Three extras we don't reach today. The first two are described in project/frontend/README.md; the third is a habit rather than a lab.

EXTRA Lab 3 — Form validation ~20 min

Create project/frontend/js/validate.js with a validateCaseForm(formData) function returning { valid, errors }.

  • Subject must be at least 10 characters
  • IBAN must match the Dutch format (NL\d{2}[A-Z]{4}\d{10})
  • Customer name must not be empty
  • Description at most 500 characters
Validation rules are exactly the kind of thing Copilot gets 90% right and 10% dangerously wrong. Good practice at reviewing rather than accepting.

EXTRA Lab 6 — Performance ~20 min

In project/frontend/js/components/case-list.js:

  1. Wrap the search handler in a debounce (300 ms)
  2. Replace the append-one-by-one loop with a DocumentFragment
  3. Stretch: render only the visible cards (a simple virtual list)

Ask Copilot to explain why each change is faster — not just to make it.

EXTRA Self-review before you open a PR ~15 min

Take any file you changed today and, in Ask mode:

Review this file the way a senior reviewer at a bank would. Focus on XSS, PII exposure, accessibility and anything a reviewer would ask me to change. List findings as: RISK | LOCATION | RECOMMENDATION.

Then fix what you agree with — and note what you disagree with, and why.

Part 3 — On your own, in your real work

These are the ones that actually change how you work. None of them use the sample app — they use your repository.

ON YOUR OWN A · Write instructions for your own repo ~30 min

Create .github/copilot-instructions.md in a repository you actually work in. Look at project/backendfrontend/.github/copilot-instructions.md for the shape.

Start by asking Copilot to draft it from your own codebase:

#codebase Read this project and draft a .github/copilot-instructions.md that captures how we actually write code here: language and framework versions, folder structure, naming conventions, error handling, testing approach, and any security rules that apply. Only state conventions you can see evidence of in the code. Where you are unsure, list it as an open question instead of guessing.

Then edit it by hand — the draft is a starting point, not the answer.

Highest return of anything on this page. Every prompt anyone on your team writes from then on starts with your standards already loaded.

ON YOUR OWN B · Turn your most-repeated review comment into an agent ~20 min

Think of the comment you leave on pull requests over and over. Write it once as an agent in .github/agents/, using today's reviewer agent as the template.

  • Give it the questions you always end up asking
  • Give it an output format your team will actually read
  • Run it on your last three merged PRs and see whether it would have caught anything

ON YOUR OWN C · Try Plan mode on something real ~20 min

Pick a ticket you'd normally start by guessing at. Switch the chat mode to Plan — it researches and writes an implementation plan without touching any files — then read the plan critically before letting Agent mode do anything.

Most people jump straight to Agent mode and then review a large diff. Reviewing a plan first is much easier than reviewing the code it produces.

ON YOUR OWN D · Document a decision your team actually made ~20 min

Take a real architectural decision from the last year that never got written down, and use the ADR approach from exercise 2.2 on it.

Act as a senior architect. Write an Architecture Decision Record for this decision: [describe it]. Include Context, Decision, Consequences and Alternatives Considered. Ask me up to 5 questions first if anything is unclear — do not invent constraints I have not told you about.
That last sentence matters. Without it you get a confident, plausible ADR containing reasons your team never had.

ON YOUR OWN D · Accessibility pass on a real component ~20 min

Take a component from your own product and ask:

Review this component for accessibility against WCAG AA. Check keyboard navigation, focus order, ARIA labels, colour contrast, and whether any state is communicated by colour alone. For each finding tell me the impact on a real user, not just the rule number.

Then verify a couple of the findings yourself — some will be wrong, and noticing which is the skill.

ON YOUR OWN E · Deliberately catch it being wrong ~15 min

Ask Copilot something about your own systems that it cannot possibly know — an internal service's rate limits, a team-specific convention, why a particular workaround exists. Watch whether it says "I don't know" or invents something plausible.

Do this once with your own team watching. It's the fastest way to make everyone appropriately sceptical without lecturing them.
